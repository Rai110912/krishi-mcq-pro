# Event-Driven Animation Intelligence Architecture

This document specifies the technical foundation for a future-ready, event-driven animation intelligence system for the Android learning/MCQ application. It guarantees that animations remain decoupled from business logic while enabling an adaptive, futuristic learning experience.

---

## 1. Vision

Animations must be a **RESPONSE to application state**, never the source of truth. The system allows the application to react naturally to user behavior without tightly coupling visual effects to the core MCQ engine.

**Core Data Flow:**
```text
USER ACTION (e.g., Selects Option A)
       ↓
APPLICATION STATE (MCQ Engine validates answer, updates stats)
       ↓
SEMANTIC EVENT (Dispatches strongly-typed Event Object)
       ↓
ANIMATION ORCHESTRATOR (Evaluates queue, priority, and budget)
       ↓
Rive / Lottie / 3D / Native (Selected renderer executes)
       ↓
VISUAL + AUDIO + HAPTIC RESPONSE
```

---

## 2. Semantic Event Architecture

The animation system communicates via a strongly typed event model. **No sensitive personal data (PII) is ever exposed to the animation payload.**

**Event Payload Structure:**
- `eventId`: Unique UUID for deduplication.
- `eventType`: Enum (e.g., `ANSWER_CORRECT`).
- `timestamp`: Unix epoch.
- `priority`: Enum (Critical, High, Normal, Low, Background).
- `source`: Origin (e.g., `MCQ_Engine`, `Profile_Screen`).
- `context`: Non-PII metadata (e.g., `streakCount`, `xpAmount`).
- `userSessionId`: Anonymized session hash for analytics tracking (optional).
- `animationPolicy`: Optional overrides (e.g., `forceMinimal`).
- `accessibilityPolicy`: Contextual overrides (e.g., `requiresTextFallback`).

---

## 3. Core Events

The system supports the following standard semantic events:
- `ANSWER_CORRECT`, `ANSWER_WRONG`, `ANSWER_SKIPPED`
- `QUESTION_COMPLETED`, `QUESTION_REVIEWED`
- `XP_GAINED`, `XP_LOST`
- `STREAK_STARTED`, `STREAK_INCREASED`, `STREAK_BROKEN`
- `LEVEL_UP`
- `DAILY_GOAL_STARTED`, `DAILY_GOAL_PROGRESS`, `DAILY_GOAL_COMPLETED`
- `TOPIC_MASTERED`, `WEAK_TOPIC_DETECTED`
- `MOCK_EXAM_STARTED`, `MOCK_EXAM_COMPLETED`
- `ACHIEVEMENT_UNLOCKED`, `MILESTONE_REACHED`
- `SESSION_STARTED`, `SESSION_COMPLETED`
- `SUCCESS`, `ERROR`, `LOADING`

---

## 4. Future Adaptive Events

The architecture supports injecting intelligent events derived from legitimate application analytics/state systems, without rewriting the rendering pipeline.

**Examples of Future Intelligent Events:**
- `LEARNING_MOMENTUM_HIGH` / `LEARNING_MOMENTUM_LOW`
- `FOCUS_DROP_DETECTED` (e.g., long pauses between answers)
- `COMEBACK_DETECTED` (e.g., correct answer after 3 failures)
- `CONSISTENCY_MILESTONE`
- `PERSONAL_BEST_REACHED`
- `MASTERY_THRESHOLD_REACHED`

*Rule: These events must be generated by state systems (not invented by the UI) and must remain completely anonymous/non-PII.*

---

## 5. Animation Orchestration

The centralized `AnimationOrchestrator` acts as the brain between the event bus and the renderers. It is strictly responsible for:
- Event prioritization.
- Animation renderer selection.
- Queue management and cancellation.
- Deduplication and interruption handling.
- Fallback degradation and accessibility compliance.
- Device capability and performance budget enforcement.

The orchestrator remains 100% independent of the MCQ engine, authentication, cloud sync, and core analytics.

---

## 6. Priority System

Events are assigned strict priorities. In the event of a conflict, higher priority wins, and lower priority is safely cancelled or deferred.

| Level | Example | Conflict Resolution |
| :--- | :--- | :--- |
| **CRITICAL** | `LEVEL_UP` | Interrupts all. Clears queue. Cannot be interrupted. |
| **HIGH** | `ACHIEVEMENT_UNLOCKED` | Interrupts Normal/Low. Queues behind Critical. |
| **NORMAL** | `ANSWER_CORRECT` | Overwrites previous Normal. Yields to High/Critical. |
| **LOW** | `BUTTON_PRESS` | Dropped if system is busy. |
| **BACKGROUND** | `LEARNING_MOMENTUM_HIGH`| Runs only if system is completely idle. |

---

## 7. Animation Selection Intelligence

The Orchestrator dynamically resolves the best renderer using a future-ready selection formula:

`Event Payload` + `Device Capability` + `Performance Budget` + `Accessibility Config` + `Asset Availability` = **Best Animation Renderer**

The system MUST choose the **LIGHTEST suitable renderer**:
- Native CSS/UI (Lightest)
- Lottie (Light)
- Rive (Moderate/Interactive)
- 3D (Heaviest/Premium)
- Static (Fallback)

---

## 8. Adaptive Animation Policies

The architecture supports dynamic scaling of animation intensity based on context.

**Examples:**
- **First correct answer:** → Subtle positive reaction.
- **Long streak:** → Stronger celebration (fireworks).
- **Major milestone:** → Premium 3D experience.
- **Low-end device detected:** → Force lightweight Lottie/Rive regardless of milestone.
- **Reduced-motion user:** → Minimal/Static feedback.

*(Note: Clean interfaces allow this logic to exist now, preparing for future AI/Machine Learning policies without refactoring).*

---

## 9. Animation Budget

Every screen/session operates under a strict performance budget.
- Limits on simultaneous animations (e.g., Max 3 Lotties, 1 Rive instance).
- CPU/GPU usage thresholds.
- Memory/VRAM caps.
- Caps on concurrent audio/haptic threads.

**Budget Exceeded:** If the budget is saturated, the Orchestrator automatically reduces or cancels low-priority effects. Core application functionality is NEVER sacrificed for visuals.

---

## 10. Event Deduplication

To prevent duplicate events from spawning overlapping UI glitches (e.g., 3 `ANSWER_CORRECT` events spawning 3 identical confetti pops simultaneously):
- The Orchestrator hashes the `eventId` + `eventType`.
- Events within a tight time window (e.g., 300ms) with identical hashes are debounced/deduplicated.
- Strict idempotency rules apply to state transitions.

---

## 11. Event Lifecycle

Every animation event moves through a strictly observable state machine:
1. `CREATED`: Event dispatched by App State.
2. `QUEUED`: Orchestrator evaluates budget/priority.
3. `RUNNING`: Renderer is actively playing.
4. `INTERRUPTED`: A higher priority event took over.
5. `COMPLETED`: Animation finished naturally.
6. `CANCELLED`: Dropped before running (e.g., screen changed).
7. `FAILED`: Asset missing or renderer crashed.

---

## 12. Fallback Architecture

If an animation fails, crashes, or is unsupported, the system gracefully cascades downwards. Animation failure MUST NEVER crash the application.

**Primary:** `Rive` / `Lottie` / `3D`
**Fallback:** `Native Android Animation` (XML/Compose/CSS)
**Final:** `Static UI Feedback` (Color change, Toast, Text)

---

## 13. Audio + Haptic Synchronization

Visuals, sound, voice, and haptics are treated as independent, synchronized layers.
- `ANSWER_CORRECT` → Rive Visual + Lottie Particles + Success Chime + Haptic + Voice Assistant.
- **Independence:** If the user's phone is on silent, visuals and haptics continue. If haptics are disabled in OS settings, visuals and audio continue. If voice fails to fetch, visuals proceed without blocking.

---

## 14. Offline-First

Animation events must work 100% offline. Core events (`CORRECT`, `WRONG`, `LEVEL_UP`) cannot depend on network connectivity. The MCQ engine must never be blocked waiting for an animation service or remote asset.

---

## 15. Performance-Aware Rendering

Before executing any high-fidelity animation, the Orchestrator must query the device's current state:
`check(DeviceCapability + CurrentLoad + AnimComplexity + Accessibility)`
If the device is thermal throttling or frames are dropping, the Orchestrator instantly downgrades the payload to a lighter renderer.

---

## 16. Debugging & Observability

A development-only "Animation Debug Mode" is mandated. When enabled via secure developer options, it overlays a HUD showing:
- `Event Name` & `Timestamp`
- `Priority` & `Selected Renderer`
- `Execution Time` & `Dropped Count`
- `Fallback Reason` & `Current Queue`
- `Performance Budget Allocation`

*This HUD must be stripped/disabled in production builds.*

---

## 17. Analytics Safety

Animation analytics only collect necessary technical metrics:
- Success/Failure rates.
- Renderer utilized.
- Duration of playback.
- Performance drops/janks.
- Asset loading failures (404s).

*Strict Rule: Never collect PII, exact quiz content, or sensitive user data in the animation analytics pipeline.*

---

## 18. Testing Matrix

The Orchestrator must pass the following structural tests:
- [ ] **Multiple simultaneous events** (Queue handles burst traffic).
- [ ] **Rapid answers** (Debouncing works).
- [ ] **Priority conflicts** (Critical interrupts Normal).
- [ ] **Renderer failures** (Rive/Lottie/3D unavailable → Static Fallback).
- [ ] **Offline mode** (Bundled assets execute).
- [ ] **Low-end devices** (Performance budget triggers downgrades).
- [ ] **Accessibility** (Reduced motion forces static feedback).
- [ ] **Sensory Independence** (Voice/Haptic disabled does not break visuals).
- [ ] **Lifecycle** (App backgrounding/navigation cancels running events safely).

---

## 19. Future AI Integration

The architecture exposes an extension point: `AnimationPolicyEngine`.
In the future, an on-device AI/ML model could feed into this engine using non-PII inputs (learning state, device capability, momentum) to recommend dynamic animation styles/intensity. 
**Constraint:** The `AnimationPolicyEngine` only recommends visual flair; it MUST NOT control core learning correctness, grading, or business logic.

---

## 20. Golden Rule

The animation system must always be:
**SAFE • FAST • MODULAR • INTERRUPTIBLE • OFFLINE-FIRST • ACCESSIBLE • PERFORMANCE-AWARE • FUTURE-READY**

*The application's educational functionality always takes absolute priority over any animation.*
